# PRD 작성

## 입력과 산출물

- 입력은 프로젝트 기획서다. 실행 요청에서 지정한 파일을 우선 사용하고, 지정이 없으면 `docs/SERVICE_PLAN.md`를 사용한다. 필요한 경우 `docs/`의 문제 카드, 자료 카드, `asis-tobe.md`를 확인한다.
- 출력은 프로젝트 루트 기준 `tasks/prd-[서비스명].md`다. 요청이나 기존 문서에 지정된 파일명용 서비스명이 있으면 그대로 사용한다. 처음 정하는 경우 기획서의 서비스명에서 공백은 하이픈으로 바꾸고 파일명에 사용할 수 없는 문자는 제거한다. 이 이름을 후속 문서에도 동일하게 사용한다.
- 실행 범위는 PRD 작성과 검토다. 기존 PRD는 사용자 요청이 기존 문서의 개정을 포함할 때 수정한다.

## 절차

1. 기획서를 읽어 사용자, 업무 상황, 문제 근거, 목표, 핵심 사용자 흐름을 파악한다. 기획서를 찾지 못하면 확인한 경로와 필요한 입력을 알린다. 보조 자료를 읽을 수 없는 경우 확인이 필요한 항목을 기록하되 기획서로 확정 가능한 부분을 작성한다.
2. 검증된 사실, 사용자 문제에 관한 가설, 구현에 영향을 주는 미결 사항을 명시한다. 입력 데이터를 확인할 수 있으면 경로·형식·실제 필드를 대조한다. `data/`의 원본은 읽기 전용으로 사용한다.
3. 아래 구성을 따라 작성한다. 기획서가 정한 우선순위와 기술 조건을 따르고, 제안 단계인 기술 결정은 제안으로 표기한다.
4. 요구사항과 인수 기준이 기획서에 부합하는지 확인한다. 저장한 경로, 필수 기능, 확인이 필요한 사항을 학생에게 짧게 알린다.

## PRD 구성

1. **개요와 목표** · 서비스명, 사용자, 문제, 기대하는 변화, 근거 및 가설
2. **사용자 흐름** · 사용 조건, 입력, 행동, 화면 또는 산출물, 예외 흐름
3. **기능 요구사항** · 각 항목에 `FR-01` 형식의 고유 ID, 우선순위, 동작과 확인 기준을 부여한다.
4. **데이터와 운영 조건** · 입력 경로, 형식, 주요 필드, 집계나 변환 규칙, 누락·오류·빈 결과 처리. 데이터가 필요한 프로젝트에 해당하는 항목을 작성한다.
5. **첫 구현 범위와 후속 범위** · 이번 실습에서 구현할 항목과 후속 항목
6. **인수 기준** · 요구사항 ID에 연결하고, 주어진 조건과 입력, 수행 동작, 관찰 가능한 예상 결과를 제시한다. 기획서 또는 확인된 자료에 기준값이 있으면 함께 기록한다.
7. **근거와 미결 사항** · 참조 파일 경로, 남은 결정, 구현에 미치는 영향
